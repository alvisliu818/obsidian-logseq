## 主库无语言代码块 读态/编辑态样式不一样 — 真因已修(23:xx)

- 用户两张截图:读态(IMG1)文字小而窄、行距乱;编辑态(IMG2)Cascadia 15px。像素取证(PIL 采样):**两图工具栏/盒子背景完全相同**,差异只在文字层。
- **真因**:UA 样式表对 `code` 直接声明 `font-family: monospace`,切断了从(已钉住!important 的)pre 的字体继承;且 Chromium 对"字号来自继承的 generic monospace"应用**固定字号默认值 13px**作为使用字号(computed 仍报 15px!)。无语言块中招;有语言块因主题的 `code[class*=language-]` 字体规则幸免。
- 关键手法:**Range.getBoundingClientRect 量 10 字符的实际渲染宽度**(7.5 vs 8.79px/char)——computed style 对这个怪癖完全失明。用户一句"现在截图整个app就是第一张图"给了我活体现场捕获,一击定位。
- 修复:`pre code { font-family/font-size(1em)/line-height: inherit !important }`(并入原 white-space/display 规则)。热重载后实测三块全部 8.79px/char Cascadia 15px,两态一致。
- 同场加防御:编辑态 `.lgp-code-editing` 的文字/盒声明全部 !important(防 adoptedStyleSheets 层叠变数)。
- 教训:computed style ≠ 渲染结果;探测遗留的编辑会话会污染后续探针;用户窗口(850px、双侧栏、DPR 1.5)要完全复刻才复现得了。

## 经验总结(全天浓缩)

1. UA 对 `code/kbd/samp` 直接声明 `font-family: monospace`——父级钉死字体也继承不进;自定义 `pre code` 必须在 code 上显式再钉。
2. Chromium 怪癖:generic monospace + 继承字号 → 使用字号被换成浏览器固定字号默认(13px),computed 仍报 15px。**computed style 会说谎**。
3. 主题 `code[class*=language-]` 特判掩盖 bug——无语言变体永远单独测。
4. 字体/字号之争量渲染像素:Range.getBoundingClientRect 量 N 字符宽度,一个数字定案。
5. 用户截图像素取证(背景色/行距/字符宽)几分钟杀死一堆错误理论。
6. 用户的活体现场 > 复现尝试:用户说"现在就是"→ 立即 CDP 全屏截图,80 步滚动抓不到的东西现场一击命中。
7. 错误理论靠证据处死;用户的每次纠正("不是旧构建"/"滚动就能复现"/"不用进编辑态")都在压缩搜索空间。
8. 探针是第一嫌疑人:合成事件无坐标=(0,0) 走不同分支;遗留编辑会话污染后续探测;openFile 对已开 leaf 不重渲染。
9. CSSOM 盲区:document.adoptedStyleSheets(CM6 StyleModule)不在 document.styleSheets。
10. 部署验证两级:磁盘 md5 + 页面内行为;修复后 CDP 热重载插件,用户免重启。
